# FitBack 하네스 오케스트레이터

## Why

FitBack은 AGENTS.md의 "카파시 4원칙"(모호하면 질문, 수술적 변경, 단계별 확인)을 강제하는 프로젝트다. 그래서 이 하네스는 팀원들이 자율적으로 계속 대화하며 진행하는 방식보다, **각 Phase 경계에서 사용자에게 결과를 보고하고 다음 단계 진행 여부를 확인받는 방식**을 기본으로 한다. FE/BE가 서로 실시간 조율할 필요는 크지 않고(계약은 이미 [[fitback-roi-logic]]에 문서화됨), 그보다는 "만들고 → 검증하고 → 사용자가 확인"하는 흐름이 이 프로젝트의 작업 원칙과 맞는다.

**실행 모드: 서브 에이전트 (기본) — 사유는 위 Why 참조.** 팀(TeamCreate) 대신 `Agent` 도구로 필요한 에이전트만 호출하고, 결과를 오케스트레이터(메인 스레드)가 수집해 사용자에게 보고한다.

## Phase 0: 컨텍스트 확인

작업 시작 전 항상 다음을 확인한다:

1. `_workspace/` 폴더가 있으면(이전 실행 산출물) 읽는다.
2. 사용자가 부분 수정/재실행을 요청했으면(예: "QA만 다시", "프론트만 수정") → 해당 에이전트만 재호출.
3. 사용자가 새 기능을 요청했으면 → 새 실행. 기존 `_workspace/`가 있으면 `_workspace_prev/`로 옮긴 뒤 시작.
4. 요청이 화면/UI 국한(FE만), Edge Function/스키마 국한(BE만), 아니면 양쪽 다 걸치는지 범위를 먼저 판단한다 — 불필요한 에이전트를 부르지 않는다(수술적 변경 원칙).

## Phase 1: 범위 판단 및 실행

**작업 범위별 분기:**

- **FE 단독** (화면/컴포넌트/스타일): `fitback-frontend`만 호출.
- **BE 단독** (마이그레이션/Edge Function/계산 로직): `fitback-backend`만 호출.
- **FE+BE 걸침** (새 기능이 화면+데이터 양쪽 필요): 두 에이전트를 **병렬**로 호출한다(서로 의존관계 없이 각자 담당 파일만 건드리므로 `run_in_background: true`로 동시 실행 가능). 단, BE가 만드는 타입/응답 shape을 FE가 그대로 소비해야 하면, BE를 먼저 실행해 계약을 확정한 뒤 FE를 실행하는 **순차 방식**으로 전환한다 — 이 판단은 오케스트레이터가 요청 내용을 보고 결정한다.

각 `Agent` 호출에는 `model: "opus"`를 명시한다.

```
Agent(subagent_type: "fitback-frontend", prompt: "<구체적 작업 지시 + 관련 파일 경로>", model: "opus")
Agent(subagent_type: "fitback-backend", prompt: "<구체적 작업 지시 + 관련 파일 경로>", model: "opus")
```

작업 지시 프롬프트에는 반드시 다음을 포함한다: 요청 원문, 관련 기존 파일 경로(에이전트가 탐색 낭비 없이 바로 열람), 변경 완료 후 변경 파일 목록을 명시적으로 반환하라는 지시.

## Phase 2: 산출물 저장

각 에이전트의 결과(변경 파일 목록, 요약)를 `_workspace/{phase}_{agent}_summary.md`에 기록한다. 예: `_workspace/01_frontend_summary.md`. 실제 코드 변경은 파일 시스템에 바로 반영되어 있으므로(파일 기반 전달), 이 요약은 QA와 사용자 보고용 인덱스 역할만 한다.

## Phase 3: QA 검증 + 디자인 검토

FE/BE 작업이 끝나면 `fitback-qa`를 호출해 [[fitback-qa-checklist]] 방법론(기계적 규칙 검사)으로 점검한다. FE가 화면/UI를 건드렸으면 `fitback-design`도 [[fitback-design-review]] 방법론(시각적/UX 품질 판단)으로 **병렬 호출**한다 — 둘은 다른 축을 보므로 동시 실행해도 결과가 충돌하지 않는다. BE 단독 작업(마이그레이션/Edge Function만)이면 `fitback-design`은 호출하지 않는다.

```
Agent(subagent_type: "fitback-qa", prompt: "다음 변경 파일을 검증: <파일 목록>. fitback-qa-checklist 스킬 방법론 사용.", model: "opus")
Agent(subagent_type: "fitback-design", prompt: "다음 화면을 디자인 검토: <파일 목록> + (있으면 Figma 링크). fitback-design-review 스킬 방법론 사용.", model: "opus")
```

QA 결과는 `_workspace/02_qa_report.md`, 디자인 검토 결과는 `_workspace/03_design_report.md`에 저장한다.

## Phase 4: 사용자 보고 및 확인

QA 결과, 디자인 검토 결과(있으면), 변경 요약을 사용자에게 보고하고, 다음 중 하나를 확인받는다:
- 위반/개선 제안 없음 → 다음 단계(커밋 등) 진행 여부만 확인.
- QA 위반 발견 → 수정 필요 여부, 어느 에이전트가 수정할지 확인 후 Phase 1로 돌아가 해당 에이전트만 재호출.
- 디자인 개선 제안 발견 → 제안은 QA 위반과 달리 "권장"이므로, 사용자가 반영 여부를 직접 결정하게 한다(자동으로 위반 취급해 재작업시키지 않는다). 반영하기로 하면 `fitback-frontend`를 재호출.

**사용자 확인 없이 자동으로 커밋/푸시하지 않는다** — AGENTS.md 작업 원칙(단계별 확인)에 따른다.

**예외 — 무인 반복(ralph-loop) 모드**: 이 사후 확인 게이트는 저위험·확정된 백로그에 한해 사전승인 이진 조건(fitback-qa 위반없음 + lint 통과)으로 대체될 수 있다. 이때도 push는 항상 사람이 직접 수행한다. 백로그 선정 기준·프롬프트 설계·게이트 상세는 [[fitback-ralph-backlog]] 스킬을 따른다.

## 에러 핸들링

- 에이전트가 실패하거나 모호함을 이유로 질문을 반환하면, 그 질문을 그대로 사용자에게 전달한다(오케스트레이터가 임의로 답하지 않는다).
- 한 에이전트가 실패해도 다른 에이전트 결과는 보존하고, 실패한 부분만 재시도(최대 1회) 후에도 실패하면 사용자에게 보고하고 다음 단계는 보류한다.
- QA가 "확인 필요"로 표시한 항목은 위반으로 단정하지 않고 사용자에게 그대로 전달한다.

## 데이터 전달 전략

| 전략 | 사용처 |
|------|--------|
| 파일 기반 | 실제 코드 변경(FE/BE가 직접 파일 수정), `_workspace/` 요약 |
| 반환값 기반 | 각 `Agent` 호출의 최종 텍스트를 오케스트레이터가 수집해 다음 Phase 프롬프트에 반영 |

## 테스트 시나리오

**정상 흐름**: "ROI 대시보드에 만료 임박 배지 추가해줘" → 범위 판단(FE 단독, `dashboard.ts` 값 그대로 소비) → `fitback-frontend` 호출 → `fitback-qa`가 토큰/손익컬러 3중 표기 확인 → 위반 없음 보고 → 사용자 확인 후 종료.

**에러 흐름**: "체크인 API에 지오펜스 없이 수동 출석 버튼 추가해줘" → `fitback-backend` 호출 시 에이전트가 AGENTS.md 출석 검증 규칙(확정) 위반 소지를 감지하고 verified 플래그 설계를 질문으로 반환 → 오케스트레이터가 그 질문을 그대로 사용자에게 전달 → 답변 받은 뒤 Phase 1 재개.
