# FitBack 하네스 오케스트레이터

각 단계에서 수술적 변경과 사용자 확인 원칙을 지킨다. 단순 질문과 설명에는 사용하지 않는다.

## Phase 0: 범위 확인

1. `_workspace/`에 이전 실행 산출물이 있으면 먼저 읽는다.
2. 부분 재실행 요청은 필요한 역할만 다시 호출한다.
3. 새 요청은 FE, BE, FE+BE, 설정 작업 중 어디에 해당하는지 판단한다.
4. 기존 사용자 변경을 보존하고 관련 없는 에이전트를 호출하지 않는다.

다음 중 하나라도 해당하면 하네스를 생략하지 않는다.

- 변경 파일이 3개 이상으로 예상된다.
- `src/components/`, `src/features/`, `src/app/` 아래 새 파일을 만든다.
- 화면 섹션이나 레이아웃을 전면 재구축한다.

1~2줄 토큰, 문구, asset, 기존 prop 조정과 순수 질문은 직접 처리할 수 있다.

## Phase 1: 실행

- FE: `fitback-frontend`
- BE, 스키마, Edge Function, ROI 계산: `fitback-backend`
- 앱 코드가 아닌 설정 작업: 오케스트레이터가 직접 처리
- FE와 BE가 독립적이면 병렬, 응답 타입에 의존하면 BE 후 FE 순차 실행

에이전트를 호출할 때 요청 원문, 관련 파일, 담당 범위, 변경 파일 목록 반환 요구를 포함한다. 여러 작업자가 같은 저장소를 공유하므로 다른 변경을 되돌리지 말라고 명시한다.

## Phase 2: 산출물

에이전트 사용 시 결과를 `_workspace/{phase}_{agent}_summary.md`에 기록한다. 설정 작업처럼 직접 처리한 경우 별도 요약 파일을 만들지 않아도 된다.

## Phase 3: 검증

앱 코드 변경 후 `fitback-qa`로 `fitback-qa-checklist`를 실행한다. UI 변경이면 `fitback-design`의 `fitback-design-review`도 실행한다. 설정 전용 변경은 해당 형식(JSON/TOML/JS/shell)과 동작을 직접 검증한다.

## Phase 4: 보고

변경 요약과 검증 결과를 사용자에게 보고한다. QA 위반은 자동으로 숨기지 않으며 디자인 제안은 권장 사항으로 구분한다. 사용자 승인 없이 커밋하거나 푸시하지 않는다.

에이전트 실패나 모호한 질문은 임의로 답하지 말고 사용자에게 전달한다. 실패한 부분만 한 번 재시도하고, 계속 실패하면 보류 상태로 보고한다.
